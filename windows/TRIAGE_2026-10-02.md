## 1. 分诊结论

1. **WT-01 是真正的 P0，并且比原报告写得更严重。** 默认配置（启动预加载）+ 首启无模型时，

   那个旧 Task。用户只能重启应用。这条必须第一个修。

3. WT-05、WT-07、WT-16、WT-17、WT-20 原方案过大。各自只保留**低成本、可确证**的那部分，
   其余移出本轮。
4. WT-13（重采样）原报告定为"协议风险"。核对 WDL 源码后，确认每次 WASAPI 回调的尾部都会进入
   flush 分支。在这个分支里，插值会用临时补零，随后丢弃滤波历史，可能影响**所有 44.1/48kHz 设备**

5. WT-14、WT-15、WT-18、WT-19 以及性能实验整体移出。它们属于收益未测量的优化、诊断增强或产品设计，

#### T1-1 WT-01：加载任务占位（P0）

**确证时序**（默认 `preload_on_launch=true`，首启无模型）：

1. `PreloadAsync` 调用 `StartLoad(false)`，后者调用 `RunLoadAsync`。
2. `LoadAsync` 定位不到模型，同步执行 `SetState(ModelMissing)` 后返回。
3. `RunLoadAsync` 的 finally 执行 `_inFlightLoad = null`。
4. 回到 [StartLoad:125](Asr/AsrService.cs#L125)，把**已完成**的 Task 写回 `_inFlightLoad`。
5. 此后两条路径都被堵死：
   - 下载完成后，`FinishModelDownloadAsync` 调用 `ReloadAsync`，只设置 `_pendingReload` 并返回旧 Task，
     而没有任何代码再消费这个请求。
   - `PrepareWithoutLoading` 因为 `_inFlightLoad` 非空直接返回。

用户手动点"重新加载模型"也走同一条死路，只能重启应用。

**方案**：先发布占位任务，再启动工作；清理时匹配任务身份。

```csharp
private TaskCompletionSource? _inFlightLoad; // 替换原来的 Task? 字段

private Task StartLoad(bool unloadFirst)
{
    var tcs = new TaskCompletionSource(TaskCreationOptions.RunContinuationsAsynchronously);
    _inFlightLoad = tcs;            // 先发布：同步完成、状态回调重入都能看到"有加载在飞"
    _ = RunLoadAsync(unloadFirst, tcs);
    return tcs.Task;
}

private async Task RunLoadAsync(bool unloadFirst, TaskCompletionSource tcs)
{
    try
    {
        if (unloadFirst) await UnloadNowAsync(dueToIdle: false).ConfigureAwait(true);
        await LoadAsync().ConfigureAwait(true);
    }
    catch (Exception ex) { AppLog.Error("asr", "加载任务异常", ex); } // LoadAsync 已转 Failed；这里只兜底
    finally
    {
        if (ReferenceEquals(_inFlightLoad, tcs)) _inFlightLoad = null;
    }
    if (_pendingReload) { _pendingReload = false; _ = StartLoad(unloadFirst: true); }
    tcs.TrySetResult();
}
```

要点：

- `PreloadAsync`、`ReloadAsync`、`PrepareWithoutLoading` 一律改判 `_inFlightLoad is not null`，并返回
  `_inFlightLoad.Task`。
- 原实现在 `_pendingReload` 时 `await ReloadAsync()`，链上的调用方会等到合并重载结束。新实现应保持
  这一点：tcs 在合并重载完成之后才完成。上面的示意写法会提前完成，实施时改为
  `await StartLoad(true)` 之后再 `TrySetResult`。
- `RunLoadAsync` 的异常不能静默吞掉，按 AGENTS.md 记录日志。`LoadAsync` 内部已经 catch 并转成
  `Failed` 状态，所以这里只是兜底。

**测试**（基于 T1-0 接缝）：

- `locate` 先返回 null、后返回 bundle：首次 `PreloadAsync` 进入 ModelMissing，随后 `ReloadAsync` 调用
  `build` 恰好一次，最终进入 Ready。
- `build` 分三种情况：同步返回、经 pump 异步返回、抛异常。每种情况结束后 `_inFlightLoad` 都为空，
  并且下一次 `ReloadAsync` 能真正重试。
- 加载中连续调用 3 次 `PreloadAsync`：`build` 只被调用一次。
- 加载中调用 `UpdateConfig` 修改 threads：最终用新 threads 构建（`build` 收到的参数），且只追加一次重载。
- `OnStateChange` 回调里同步调用 `PreloadAsync`（模拟重入）：不会产生第二次加载。

**手工验证**（Windows 真机）：删除模型目录后启动 → 自动下载 → 下载完成后**不重启**即进入就绪
并能听写；断网让下载失败 → 恢复网络后手动重试 → 就绪。

#### T1-2 WT-02：会话租约，防止空闲卸载释放活跃引擎

**确证**：

- `LoadAsync` 完成后无条件调用 `ScheduleIdleUnloadIfNeeded()`（[AsrService.cs:248](Asr/AsrService.cs#L248)），
  即使这时正处在一次冷恢复的录音中。
- `LocalAsrSession.EnsureBufferIfPossible` 把引擎实例交给 `RecognitionBuffer` 长期持有。
  卸载后，预览/最终识别会调用已被 Dispose 的 ORT session，抛异常后本次听写丢失。
- 计时器已把卸载排入 pump 后，即使再开始新会话，`MakeSession` 停止计时器也撤不回这次卸载。

触发前提是用户开启了空闲卸载（默认 0）。

**方案**：

1. `AsrService` 增加 `private int _activeSessions;`（只在 UI 线程读写）和一个
   `private volatile int _sessionsSnapshot;`（供 pump 读取）。或者直接用 `Volatile`/`Interlocked`
   维护单一计数。
2. `MakeSession` 递增计数，并把"释放租约"回调传给 `LocalAsrSession`。`LocalAsrSession.Close()`
   已有 `_closed` 幂等保护，在其中调用一次即可，从而保证每个会话恰好释放一次。
   `IDictationSessionFactory.SessionEnded()` 保留为"重新安排计时"的触发点，不承担计数。
3. `ScheduleIdleUnloadIfNeeded` 开头增加 `if (_activeSessions > 0) return;`。
   `LoadAsync` 完成、`UpdateConfig` 两处调用因此自动受保护。
4. `UnloadNowAsync(dueToIdle: true)` 投到 pump 的闭包里，执行前再次检查计数：大于 0 则放弃卸载并返回
   `false`。UI 侧在 `hadEngine == false` 时不改状态，这已是现有行为。
5. 不改变"引擎只在 pump 上 Dispose"的约定。

**测试**：

- 空闲卸载设为 1 分钟，用手动 `schedule` 触发：会话进行中触发计时 → 引擎未被 Dispose
  （假引擎记录 Dispose 次数）。
- 会话进行中加载完成（冷恢复）→ 没有安排计时；会话关闭后才安排。
- 卸载闭包已入队但 pump 被一个慢任务占住，此时开始新会话 → 卸载闭包执行时放弃。
- 会话 Close 两次 → 计数只减一次。

**手工验证**：空闲卸载设为 1 分钟，等待卸载 → 按热键说约 90 秒 → 正常出字。

#### T1-3 WT-03：破坏性操作的门禁改用真实会话状态

**确证**：`ReloadModelAsync` 在拒绝重载时把 `_currentState` 改成 Error，2.5 秒后由
`ScheduleDictationErrorRecovery` 恢复成 Idle，但控制器的 `_active` 仍然存在。此后以下三个门禁都会
放行，进而可能 Dispose 正在使用的引擎或控制器：

- 第二次点"重载"
- 保存 ASR/热键/音频/LLM 设置（`SaveRecognitionAsync`）
- 开始录制热键（`BeginHotkeyRecording`）

热键健康失败（`OnHotkeyHealthChanged(false)`）也能在会话进行中把显示状态改成 Error。

**方案**：

1. `VoiceTyperController` 增加 `public bool HasActiveDictation => _active is not null;`。
2. `AppCoordinator` 增加 `private bool IsDictating => _controller?.HasActiveDictation == true;`，并把
   [L180](App/AppCoordinator.cs#L180)、[L758](App/AppCoordinator.cs#L758)、[L881](App/AppCoordinator.cs#L881)
   三处的 `_currentState.State.IsActiveDictation()` 改为 `IsDictating`。
   全仓搜索 `IsActiveDictation()`，其余仅用于**显示**的地方保持不变。
3. `ReloadModelAsync` 被拒绝时**不改** `_currentState`，也不安排错误恢复计时器，改为：
   - HUD：`_hud?.FlashWarning(...)`；
   - 设置页：把 `SetupForm.OnReloadModel` 从 `Action` 改为 `Func<string?>`（返回拒绝原因），由设置页显示在
     模型卡的消息位置。也可以新增 `ShowModelActionMessage(string)`，二选一即可，以改动最小为准。
4. `OnHotkeyHealthChanged(false)` 在 `_active is not null` 时只发 `PreviewWarning`，不发 Error 状态。
   健康恢复/失败的托盘显示在会话结束后由下一次健康回调或就绪重评估补上。

**测试**（`VoiceTyperControllerTests` 已有假依赖）：

- 录音中 `HasActiveDictation == true`；`Finish` 的所有路径（文本/失败/取消/丢弃/手势/Stop）之后为 false。
- 录音中触发热键健康失败：不发 Error 状态，会话继续，后续松键正常出字。
- 协调器层目前没有测试 harness。若为它补测试的成本过高，可以只做控制器测试，并在交付记录中写明
  "协调器门禁靠代码审查"。

**手工验证**：录音中连点两次"重新加载模型"、录音中保存设备设置、识别中尝试录制热键。三种情况下
当前听写都应正常上屏，并能看到拒绝原因。

#### T1-4 WT-06：ORT 构造失败时确定释放

#### T1-5 WT-05（收窄）：后台线程关闭不得释放仍在使用的队列

#### T3-1 WT-13：重采样流式供给的正确性

**已核实的事实**（NAudio 2.2.1 源码）：

- `WdlResamplingSampleProvider.Read` 以拉取模式调用 `ResamplePrepare(framesRequested)`，然后从源读取。
  当前源是 `BufferedWaveProvider(ReadFully=false)`，每次 WASAPI 回调的最后一次 Read 必然是短读。
- `WdlResampler.ResampleOut` 遇到 `nsamples_in < m_last_requested` 时进入 "flush" 分支：用临时补零的
  数据计算输出，再按估算扣减输出数，并把 `m_samples_in_rsinbuf` 减去已消耗的输入位置（可能清零）。
- 后果：每个回调边界（约 10ms 一次）的插值都用到零值，并可能丢失插值/滤波历史。默认模式是线性插值
  加 IIR 低通（非 sinc），影响幅度未知。

**第一步：写测试，不改实现。**

1. 在测试中复刻当前管线：`BufferedWaveProvider(ReadFully=false)` → `ToSampleProvider` →（立体声时）
   `ToMono` → `WdlResamplingSampleProvider(16000)`，并沿用 `OnCaptureDataAvailable` 中的读取循环。
   最好把这段循环提取成 `AudioCaptureService` 的 internal 静态方法，让测试与生产共用。
2. 输入：48kHz 与 44.1kHz、单声道与立体声、440Hz/1kHz 正弦波以及
   `macos/Tests/VoiceTyperTests/Fixtures/speech_zh_en_mixed.wav`（需要先上采样到 48k 再送入）。
   分块方式：一次性整段送入（基线），以及 10ms 固定分块和 7–13ms 随机分块。
3. 断言/报告以下指标：输出样本数与 `输入时长 × 16000` 的偏差；流式输出与一次性输出的 SNR；
   边界处的最大跳变。
4. 如果模型存在（`EndToEndRecognitionTests` 的跳过逻辑），再比较"流式重采样后识别"与"直接用 16k 原文件
   识别"的文本差异。

**第二步：判定。**

- 如果流式与一次性输出的 SNR 不低于约 40dB、样本数偏差小于 1%，就不改实现，在 DESIGN 中记录测量
  结论，关闭 WT-13。
- 否则改为**输入驱动**：直接使用 `NAudio.Dsp.WdlResampler`，设置 `SetMode(true, 2, false)`
  （与当前 provider 的默认值一致）和 `SetFeedMode(true)`。每次回调先把收到的帧全部转成 mono float，
  然后 `ResamplePrepare(inFrames, 1, ...)`，复制输入，再 `ResampleOut(out, 0, inFrames, maxOut, 1)`。
  `Stop` 时不需要额外 flush，尾部滤波延迟在 1ms 量级，可以忽略。
- 替换后，第一步的测试必须达标，并补测"连续静音输入不会持续产生非零输出"。

**注意**：这只涉及采集侧，不触及 fbank/LFR/CMVN 金标准，不需要同步修改 macOS。

#### T3-2 WT-07：是否需要独立钩子线程

**现状**：钩子回调已经用 `PostAsync` 把业务投到 UI 线程，所以回调本身不阻塞。剩下的风险是：UI 线程
忙于其他工作（打开设备、剪贴板快照、设置页渲染）时，钩子消息得不到分发，全系统按键都会因此延迟。
时间过长时，钩子还可能被系统摘除。

**第一步：采数据，不改代码。** 现有 `metrics` 日志已经包含 `PressedAt → CaptureStartedAt`，这一段
就是 `_audio.Start()` 占用 UI 线程的时长；热键自愈日志（"热键监听已失效"）记录摘钩事件。
请用户在真机上收集至少 50 次听写，分别覆盖内置麦、USB 麦和蓝牙耳机。

**第二步：判定。** 满足以下任一条件才实施：

- capture start 的 p95 超过 150ms；
- 日常使用中出现过自愈日志；
- 用户反馈过听写触发时全局按键卡顿。

**实施范围**（满足条件时）：

1. `HotkeyService` 内部创建专用 STA 线程，在该线程上 `SetWindowsHookEx` 并运行 `Application.Run()`
   或 `GetMessage` 循环。键盘钩子、鼠标钩子和 `HotkeyStateMachine` 都只在该线程上访问。
2. 对外事件仍通过 `UiDispatcher.PostAsync` 送到 UI 线程，`IHotkeyListening` 契约不变。
3. 从 UI 写入的 `AcceptsCancelWhenInactive` 改为 volatile 字段，由钩子线程读取。
   `Start`/`Stop`/重装通过向钩子线程投递消息完成，并同步等待结果。
4. 健康检查计时器移到钩子线程。
5. 必须附上真机验收：中文 IME、AltGr、右 Ctrl + 鼠标、热键录制、睡眠恢复、锁屏解锁，以及在 UI 线程
   人为 `Thread.Sleep(3000)` 的调试开关下热键仍能响应。
