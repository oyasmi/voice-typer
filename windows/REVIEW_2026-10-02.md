## 1. 总体判断

**建议保留现有单进程、WinForms、串行 ASR 的总体架构，下一轮优先修复生命周期与状态所有权，再完善设置页，最后依据测量优化推理热路径。**

当前版本已经具备不少值得保留的基础：

- 控制器用单个 `Utterance` 表示活跃听写，统一收尾并检查回调身份；这比多个录音/识别布尔值可靠。
- ASR 使用独立串行线程，预览至多一个在飞，静音跳过预览，最终对完整音频复识别，语义清楚。
- `RecognitionBuffer` 用只追加的扁平数组和快照，避免每次预览重新拼接全部录音。
- 默认预加载、默认不空闲卸载，符合高频输入工具的响应需求；需要省内存的用户仍有选择。
- 模型下载有固定 SHA256、断点续传、来源切换和诊断；LLM 默认关闭、密钥使用 DPAPI。
- HUD 不抢焦点，隐藏时停止动画；托盘图标释放原生句柄；配置和密钥采用原子替换。
- 已有 Windows CI、控制器假依赖测试、共享 ASR 金标准与真实设置窗体测试。

主要问题在于：**控制器内的单会话约束，尚未延伸到模型、采集器、剪贴板恢复和应用退出的全部生命周期。**
几个模块各自做过修补，但跨模块仍依赖“当前显示什么状态”“这个字段现在是不是 null”等间接判断。
长期运行和快速连按恰好会反复遇到这些边界。

设置页已有五页侧栏、卡片、折叠参数和统一保存，不能再按旧版“四个 Tab 大表单”评价。
不过它目前更接近整理过的配置面板，距离成熟桌面产品仍差一套一致的控件、布局和反馈设计。

## 3. 长期运行与生命周期

### WT-01：同步完成会把加载任务永久留在字段中

定位：[AsrService.cs](Asr/AsrService.cs#L122) `StartLoad / RunLoadAsync / LoadAsync`，
[AppCoordinator.cs](App/AppCoordinator.cs#L723) `FinishModelDownloadAsync`。

`StartLoad` 先调用 `RunLoadAsync`，返回后才写 `_inFlightLoad`。但 async 方法并不保证异步完成。
当模型不存在、且 `unloadFirst=false` 时，`LoadAsync` 在遇到真正的异步操作之前就返回了。

可推导出以下正常首启时序：

1. 默认开启预加载，模型缺失；`StartLoad(false)` 调用 `RunLoadAsync`。
2. `LoadAsync` 同步进入 `ModelMissing` 并返回；`RunLoadAsync.finally` 清空 `_inFlightLoad`。
3. 控制流回到 `StartLoad`，把**已经完成的 Task**重新写入 `_inFlightLoad`。
4. 下载成功后调用 `ReloadAsync`，看到字段非空，只设置 `_pendingReload` 并返回旧任务。
5. 旧任务已经执行过处理 pending 的代码，没有任何任务会再消费这个请求；模型不会真正加载。

这也会让 `PrepareWithoutLoading` 因“有加载任务”直接返回。重启进程后模型已存在，可能掩盖问题。
已经具备模型的开发环境、仅测 `ModelDownloader` 或 `SenseVoiceEngine` 的测试都不能覆盖它。

**建议**：在触发状态通知或调用 async 工作前先建立并发布加载占位任务；完成清理必须匹配任务身份。
`Loading` 时 ensure 应共享真实任务，不能只返回 `Task.CompletedTask`。
真正的 reload 要让调用方等到所请求配置版本完成，而不只是等到上一轮加载结束。
不能只增加一条“如果 Task 已完成则设 null”补丁：加载状态通知存在同步重入，必须一起约束。

**验收**：假定位器“先缺失、随后存在”，同步返回/异步返回/抛异常三类加载；一次下载完成后直接就绪；
连续 ensure 只构造一次；加载中请求新配置后最终确实使用新配置；失败后能手动重试。

### WT-02：空闲卸载与活跃会话仍能交错

定位：[AsrService.cs](Asr/AsrService.cs#L178) `MakeSession / LoadAsync / ScheduleIdleUnloadIfNeeded / UnloadNowAsync`。

`MakeSession` 会取消计时器，但服务没有活跃会话计数；加载完成和配置更新又会重新安排计时器。
例如设置空闲 1 分钟、从空闲卸载恢复后录一段接近 120 秒的语音，**加载完成后重新启动的计时器会在录音中到期**。
卸载虽然与一次正在运行的推理串行，但 `RecognitionBuffer` 仍持有已经被 Dispose 的引擎，后续预览/最终识别会失败。

另一种路径：计时器已把卸载排入 pump，用户随后开始新会话；取消计时器无法撤回已入队卸载。
`CurrentEngine` 的引用锁只保护引用读写，不保证返回的对象在会话期间始终存活。

**建议**：服务持有活跃会话租约。只有 `activeSessions==0 && engineReady && !closing` 才能安排卸载；
会话开始递增 idle 版本，排队卸载在 pump 真正执行前再次校验版本和租约。
关闭会话释放租约一次，模型释放仍在 ASR 串行线程完成。

**验收**：冷恢复后长录音、加载慢于录音开始、卸载已排队但推理线程繁忙、临到超时按热键、设置更新；
所有情况下均不得释放活跃会话的引擎。默认空闲卸载为 0，降低了常见发生率，但不能替代这个保证。

### WT-03：显示状态不能充当破坏性操作的门禁

定位：[AppCoordinator.cs](App/AppCoordinator.cs#L754) `ReloadModelAsync / SaveRecognitionAsync / BeginHotkeyRecording`，
[VoiceTyperController.cs](Core/VoiceTyperController.cs#L234) `OnHotkeyHealthChanged`。

重载模型时若正在听写，协调器把 `_currentState` 从 Recording/Recognizing 改为 Error，随后 2.5 秒恢复 Idle。
**实际 `_active` 没有结束。** 此时第二次点击重载，或者保存热键/ASR 配置，`IsActiveDictation()` 已返回 false：
重载能释放活跃引擎，保存能 Stop/Dispose 控制器，正在说的内容可能被丢弃。
热键健康错误也能形成“显示 Error、实际仍有会话”的同类状态。

**建议**：公开只读的真实忙碌状态，或由同一个运行状态模型派生 `CanReloadModel / CanApplyRecognitionSettings`。
操作拒绝、暂时告警应作为独立 notice，不覆盖听写阶段。
同样要区分“热键健康失败”“一次听写失败”“模型不可用”，不能用一个定时器把所有 Error 都恢复成 Idle。

**验收**：录音中连续两次点重载；第一次被拒后保存设备；热键自愈失败期间保存；纠错期间尝试热键录制。
均应继续保留当前听写，并展示拒绝原因。

### WT-04：采集资源应绑定一次录音，而不是共享字段

定位：[AudioCaptureService.cs](Services/AudioCaptureService.cs#L100) `Start / OnCaptureDataAvailable / OnCaptureStopped / TeardownStoppedCapture`。

有三处相互关联的问题：

- Stop 是异步请求，Start 只检查 `_running`。快速取消后重启能覆盖旧 `_capture/_device`，旧停止回调只 Dispose 旧 capture，
  没有保留与旧 capture 对应的 MMDevice 引用供确定释放。
- `OnCaptureDataAvailable` 不检查 sender，直接读取**当前** `_inputBuffer/_resampledProvider`。
  旧 capture 的在途数据能进入新录音管线；即使取字段时还属于旧录音，之后的 `AppendSamples` 也只认当前 `_running/_chunker`。
- 设备异常停止的业务处理不绑定 sender。旧设备的迟到错误能结束新录音。

已核对 [NAudio 2.2.1 WasapiCapture 源码](https://raw.githubusercontent.com/naudio/NAudio/v2.2.1/NAudio.Wasapi/WasapiCapture.cs)：
Stop 不等待完成，停止事件可投递到创建时的同步上下文。因此不能假定 Stop 返回后旧事件全部结束。

**建议**：每次 Start 创建 `CaptureContext`，拥有 capture、device、输入缓冲、重采样器、chunker、generation 和回调。
旧上下文自行释放；所有数据/电平/停止事件携带身份，在消费者处拒绝旧 generation。
如果采用后台采集所有者线程，COM 资源也在明确的所属线程创建与释放。

另有依赖层复核项：该固定版本为 event-sync 创建 `EventWaitHandle`，其 `Dispose` 未见确定释放此字段。
不能据此断言应用每次永久泄漏一个句柄：GC 可能回收它。但应测量高频 Start/Stop 的句柄趋势，并验证升级或局部适配方案。

**验收**：假 capture A 停止未完成时创建 B，再送 A 的数据/错误/停止事件；B 音频样本、设备和状态必须不变，A/B 各释放一次。
真机测试快速误触、连续 Esc 后重录、拔插 USB/蓝牙、设备失效后恢复。

### WT-05：关闭和推理故障需要独立的恢复协议

定位：[AsrPump.cs](Asr/AsrPump.cs#L89)、[AsrService.cs](Asr/AsrService.cs#L359)、
[LocalAsrSession.cs](Asr/LocalAsrSession.cs#L208)、[AppCoordinator.cs](App/AppCoordinator.cs#L123)。

`AsrPump.Dispose` 等线程 2 秒，**不检查 Join 结果**就 Dispose 队列。线程可能仍在加载/推理，随后继续枚举被释放的队列。
枚举异常发生在循环的 try/catch 之外。音频投递线程有相同关闭模式。
[BlockingCollection 的 Dispose 并不支持与其他成员并发使用](https://learn.microsoft.com/en-us/dotnet/api/system.collections.concurrent.blockingcollection-1.dispose?view=net-10.0)。

同时，协调器没有关闭标记、应用级取消源或在飞任务登记。麦克风探测、下载/加载/纠错/更新的迟到回调仍可能在退出阶段
投递 UI、更新已释放对象，或在 pump 停止接单后继续 Post。仅停止 Timer 不会撤回已投递的动作。

识别看门狗只关闭会话、丢弃结果，没有停止当前 `InferenceSession.Run`。
如果原生推理一直不返回，界面稍后恢复 Idle，新会话仍能把持有音频的闭包不断排到无界队列。
这是“当前工作真的卡死”条件下的故障放大风险；不是声称正常录音就会无限积压。

**建议**：

1. 应用进入 Closing 后停止新操作、使所有迟到 UI 回调失效，取消并追踪后台任务。
2. pump 停止接单后允许工作线程结束；只有线程结束才能释放队列。等待不得占住 UI 消息泵。
3. 单次超时进入明确的引擎健康状态，确认正在运行的任务退出后才重新开放听写。
4. 固定版本的 [RunOptions.Terminate](https://raw.githubusercontent.com/microsoft/onnxruntime/v1.24.2/csharp/src/Microsoft.ML.OnnxRuntime/RunOptions.shared.cs)
   可以请求终止使用该 RunOptions 的调用；应验证是否适用于当前模型/CPU 算子，使用每次调用独立的 RunOptions，
   并处理协作取消。不能把它当作任意原生卡死都可立即中断的保证。
5. 若原生调用不能恢复，给出实际不可用状态和重启入口，避免假装已经恢复。
   不在推理仍运行时从其他线程强行 Dispose 同一 session。

CTS 也要明确释放：会话、看门狗、剪贴板恢复目前主要 Cancel/置 null，没有完整的 Dispose 协议；
`_pendingAudio.Clear()` 保留容量，Close 后在飞闭包也可能继续持有 buffer。
应在使用方退出后释放，不宜机械地 Cancel 后立刻 Dispose 所有 CTS，以免与 token 使用竞态。

**验收**：加载/预览/final/纠错/下载/探测各阶段退出；假任务运行超过 2 秒；关闭后尝试 Post；
推理超时后重复按热键不增加待执行会话；恢复和退出不产生未处理后台异常。

### WT-06：ORT 构造必须在异常路径确定释放

定位：[SenseVoiceEngine.cs](Asr/SenseVoiceEngine.cs#L86)。

`SessionOptions` 未使用 using；`InferenceSession` 先创建，随后才解析 CMVN 和 tokens。
显式维度错误分支有 Dispose，但 `CmvnStats.Parse / LoadTokens / FbankFrontend` 的异常路径没有统一清理。
构造函数抛出后外层拿不到完整 `SenseVoiceEngine`，只能依赖资源自身最终回收。
损坏模型下反复点重载会放大资源滞留；不能称为已经测得永久泄漏。

**建议**：可解析的小文件先解析；SessionOptions 使用 using；session 在构造成功前由局部变量拥有，异常统一 Dispose。
加载期契约检查补齐数据类型、rank 和固定维度，推理期明确检查有效帧数与实际 logits 长度，避免用截短掩盖契约错误。

**验收**：损坏 CMVN、无效 tokens、错误 I/O、多次加载失败；每次构造失败的资源都释放，允许随后加载正确模型。

### WT-07：独立热键线程与异步采集启动

定位：[HotkeyService.cs](Services/HotkeyService.cs#L21)、[UiDispatcher.cs](Support/UiDispatcher.cs#L35)、
[VoiceTyperController.cs](Core/VoiceTyperController.cs#L438)。

钩子业务已经使用 `PostAsync`，这是正确的修复，但钩子本身仍安装在 UI 线程。
UI 在枚举 COM 设备、初始化 WASAPI、枚举剪贴板格式/同步重试、写配置和日志时被阻塞，钩子消息也无法及时处理。
官方说明回调在安装线程执行，超时可被静默摘除，并建议独立线程；Windows 10 1709 起最大超时为 1000ms。
[LowLevelKeyboardProc 官方契约](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)

当前健康检测在约 2 分钟无钩子活动、连续两次怀疑后才重装，且 `GetLastInputInfo` 含鼠标。
这可作为兜底，不能支撑“唤起始终快速”的保证。

**建议**：钩子和手势状态机由独立消息线程拥有，回调只判定/消费/记录时间/发送事件。
UI 继续拥有听写业务状态；跨线程的配置、Esc 窗口和暂停操作通过消息或安全快照传递，不能直接并发修改现有状态机。
采集启动交给单一后台所有者，UI 立即展示启动反馈，并在启动期间接受取消；Start 完成后仍检查会话身份。
音频格式继续是 16kHz、float32、mono，空闲时不持续占用麦克风。

特别关注右 Ctrl 的按住模式：普通 Ctrl 组合操作也会暂时开始采集，HUD 延迟 150ms 仅避免闪烁，
没有避免设备打开成本。要支持“启动未完成就发现手势作废”的取消，不能为避免成本而丢掉正常听写开头。

**验收**：UI 人为阻塞数秒时，钩子仍能返回；释放/取消事件顺序正确；中文 IME、AltGr、右 Ctrl+鼠标/滚轮、
快速手势取消、热键录制、睡眠恢复与锁屏解锁。独立线程会增加同步复杂度，应与身份检查一起提交。

### WT-08：剪贴板恢复状态需要跨听写、跨配置更新连续存在

定位：[TextInsertionService.cs](Services/TextInsertionService.cs#L129)、
[VoiceTyperController.cs](Core/VoiceTyperController.cs#L131)、[AppCoordinator.cs](App/AppCoordinator.cs#L231)。

序列号与文本双重校验、连续插入继承原始快照的方向正确，但还缺两项所有权保证：

- A 的延时结束，恢复动作已入 UI 队列；B 随后插入并生成新的 pending。A 的迟到动作虽不会覆盖 B 的剪贴板，
  却仍无条件执行 `_pendingRestore=null`，清掉 B 的恢复状态。接下来的 C 就可能把 B 当成用户原剪贴板。
- 插入服务在控制器构造时新建。A 成功后 1 秒恢复窗口内保存热键/ASR/LLM 配置，会重建控制器。
  B 若随即插入，新实例无法继承 A 的原始快照。A 的恢复因序列号变化而跳过，B 最后恢复成 A，用户原剪贴板丢失。

**建议**：插入服务由应用生命周期持有，控制器借用；每个恢复动作有 operation ID，回到 UI 后仍检查取消/身份，
只清理属于自己的 pending。快照中 Bitmap/Stream 等数据的所有权、继承和最终释放也应明确。
失败兜底复制是用户可用的最终结果，不应再被自动恢复。

性能上，逐格式快照发生在 UI/STA 上，含图片、Office/远程延迟格式时可能耗时，焦点检查又只发生在快照之前。
应测量并在注入前再校验目标/修饰键；保持原剪贴板保护，不能为了省时间只备份纯文本。
固定 1 秒恢复和 SendInput 无法证明目标实际粘贴的固有限制仍保留，不把现有架构不可能提供的确认当成验收条件。

**验收**：A 的恢复动作排队后开始 B/C；A 与 B 之间应用配置；用户期间另行复制；空/文本/图片/HTML/RTF/文件剪贴板；
目标变焦、管理员窗口、剪贴板忙、退出期间恢复。不能只测试 `ShouldInheritPendingSnapshot` 这个纯比较函数。

### WT-09：日志容量上限不覆盖常驻进程

定位：[AppLog.cs](Support/AppLog.cs#L22)。

2MB 滚动仅在 Initialize 执行，运行中没有长度检查。一次持续数周的进程可以无限增长日志；
音频处理异常若持续发生还会不断写日志。`AutoFlush=true`、全局锁和同步 WriteLine 同时把文件系统延迟传到 UI/采集/推理线程。
AutoFlush 是刷新 writer/流，并不等价于每条都做磁盘介质级同步，问题在于调用仍同步执行 I/O。

**建议**：有界日志队列与单 writer，运行中按大小滚动并限制总备份容量；高频重复错误合并为次数。
低级别日志允许计数后丢弃，错误保留明确策略；退出做有时限的 flush。
初始化/写入失败至少输出一次安全的 stderr/调试诊断，禁止静默让人以为日志可用，也避免日志失败再次递归写日志。
保留只含数值/枚举的听写摘要，异常使用脱敏上下文、类型、阶段和错误码，避免输出全文/密钥。

**验收**：单进程超过滚动阈值、磁盘不可写、持续重复错误、日志消费者慢、退出 flush；总日志大小保持上限，热路径不被 writer 阻塞。

## 4. 设置与 HUD：设计规格和行为问题

### WT-10：统一配置约束，避免“打开即修改”

定位：[AppConfig.cs](Core/AppConfig.cs#L42)、[SetupForm.cs](UI/SetupForm.cs#L168)、
[SetupForm.Layout.cs](UI/SetupForm.Layout.cs#L456)。

| 字段 | 配置校验允许 | 设置页控件允许 | 后果 |
| --- | --- | --- | --- |
| 空闲卸载分钟 | 0–1440 | 0–120 | 合法的 180 分钟被控件载入成 120 |
| LLM 超时秒 | 1–120 | 1–60 | 合法的 90 秒被控件载入成 60 |
| LLM 最大 Token | 64–8192 | 64–8000 | 8192 被控件载入成 8000 |
| HUD 不透明度 | 0.1–1 | 0.4–1 | 配置保存值、显示值和运行值不一致 |

载入后的 `_loadedConfig` 保留原值，`BuildDraft` 读取控件夹逼值，JSON 比较因此认为用户修改过。
保存其他字段时会一并覆盖这些值。温度控件只有一位小数，也应核对非整档合法值的显示/编辑语义。

**建议**：字段约束来自同一处；支持值必须能无损载入。刻意收紧范围时做显式迁移与提示。
保存接口返回实际验证/持久化后的配置，表单以它更新基线，不能无条件把提交前 draft 视为已生效配置。
改用规范化字段比较，减少 JSON 复制和逐键输入时的重复分配。

**验收**：上表合法边界与中间值打开后不 dirty、撤销不改变配置、修改无关项不夹逼其他字段；配置与控件验证规则一致。

### WT-11 / WT-12：会话参数与加载校准解耦

`UpdateConfig` 只热更新 language，只有 model_dir/threads 会触发重载。
`_resolvedPreviewWindowSamples` 则只在 `CalibratePreviewWindowIfNeeded` 改写。
因此在引擎 Ready 时修改 preview_window 并保存，新控制器虽创建了，新的会话仍使用旧窗口，直到下次真正重载。
[相关实现](Asr/AsrService.cs#L59)

自动校准也并非注释说的“首次”：每次 Load 都对 5 秒静音跑一次。
校准先入 pump，服务随即广播 Ready，新会话可在校准完成前捕获旧窗口；校准结果在 pump 上直接写 UI 读取的字段。
这些是确定的时序与开销，额外等待多长需要测量。

**建议**：显式会话参数在保存后立即用于下一会话；自动值有独立的校准结果。
校准结果按模型版本/线程设置等有效条件复用，并经 UI 消息发布；首次热身与可推理就绪语义明确。
不要在每次节能恢复时无条件插入校准，也不要把 5 秒静音的 RTF 当作 15 秒真实语音性能的充分证明。

### WT-16：HUD 保留外观，先修绘制资源和反馈稳定性

定位：[RecordingHud.cs](UI/RecordingHud.cs#L428)、[HudTextLayout.cs](UI/HudTextLayout.cs#L25)。

- `Relayout` 的 MeasureFormat、OnPaint 的 statusFormat/preview format 都创建 StringFormat，没有 Dispose。
  33ms 绘制周期下会反复产生待回收的原生资源，应该使用 using 或由窗体持有并释放。
  [StringFormat.Dispose 官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.drawing.stringformat.dispose?view=windowsdesktop-10.0)
- FitTail 已限制 400 字并缓存字符宽度，这是已有优化；但 Relayout 之前仍 Measure 整段全文。
  Wrap 对每个增长中的字符串再求和，生成较多临时字符串。优先从有上限的尾部确定档位，缓存文本/DPI/宽度对应布局。
- 宽度每次从最小档重新选择，可以随着识别修正跨档收缩；注释“按档增长避免抖动”并不保证会话内单调稳定。
  可用会话内只增宽、或延迟收窄规则，开始下一会话复位。
- 关闭系统动画后 Timer 仍 33ms 全窗重绘。录音保留必要波形刷新；识别静态时按需绘制，计时按秒更新。
- HUD 用 DateTime.UtcNow 计时，改用 Stopwatch，避免系统时钟调整影响显示。
- 跨 DPI 时 Relayout 没有重算锚点；配置改变位置也只改字段。需要真实双屏验证实际落点，再明确当前会话/下一会话生效规则。
- LLM 回落的 warning 随即被成功状态覆盖；最后可能只看到“已输入”。应让成功结果携带短暂“使用识别原文”辅助说明。
  错误正文不能与预览共用“只留最新尾部”的规则，把原因的开头裁掉；长错误提供设置诊断入口。

字体、StringFormat、绘制路径和测量缓存要统一规定所有权。设置页为每个 label `new Font`，也应采用有限的字体集合并在所属窗体退出时释放；
不能把 GC 当作原生图形资源的日常清理策略。这里没有宣称已经观测到 GDI 句柄持续上升。

### WT-18：设置状态需要独立模型

当前 partial 拆分只分了文件，[SetupForm.Layout.cs](UI/SetupForm.Layout.cs) 仍混有 BuildDraft、dirty、保存事务与注册表操作。
用户每改一个字段，就 Clone 配置并序列化两遍；所有 dirty 提示共用 footer label，继续编辑还会把保存失败说明覆盖。
LLM 测试进行时其他字段可以继续修改，完成后结果可能被误解为“当前新字段已经测试成功”。

**建议**：增加轻量的 `SettingsDraft`：saved/draft、字段错误、是否修改、是否保存中、外部状态版本。
表单负责显示和输入；应用服务负责持久化、密钥/自启的部分成功与运行配置应用。
一次测试绑定不可变的地址/模型/密钥快照，输入改变后标记测试结果过期，窗口关闭能取消。
现有测试 API 没有 CancellationToken，补传播而不是在底层传 `CancellationToken.None`。

即时动作（下载、重载、检测、测试）与待保存参数要清楚区分：
例如用户选了“不预加载”但未保存，此时点下载，运行行为仍基于已保存设置。
应在模型卡说明当前实际运行策略，或者明确要求先保存相关变更；不能偷偷保存整个草稿。

开机自启有托盘与设置两入口：托盘勾选不会刷新当前设置草稿基线，设置保存后托盘也未主动同步勾选。
保留跨页/关闭草稿，但未修改该字段时刷新外部实际值，发生冲突时明确处理。
密钥保持 DPAPI；测试结果、日志和错误消息不携带密钥或真实用户全文。

### WT-19：设置页视觉与交互设计建议

建议继续使用当前 WinForms，保留五项侧栏；先做一套小而一致的设计规范，覆盖原生控件的常见粗糙感。
HUD 的暗色强调“录音反馈”，设置页的浅色强调“可配置与可阅读”，两者无需强行使用相同背景。

#### 当前实现的具体不足

定位：[SetupForm.Layout.cs](UI/SetupForm.Layout.cs#L27)、[SetupForm.cs](UI/SetupForm.cs#L111)。

1. 默认 1080×800、最小外框 860×640，侧栏固定 178px，字段说明/编辑器固定 52%/48%。
   长地址、模型名和设备名却只有不到一半的内容宽度；小屏高缩放尤其局促。
2. 卡片、行、字号和颜色在方法中各自硬编码，常规描述 8pt 偏小；编辑器直接使用原生紧凑高度，
   文字块高度与控件高度不协调。侧栏选中态只有颜色变化，没有独立可辨认的标记。
3. 模型处处有行动按钮，而主保存也用同样的蓝色强强调；同一页主次动作不够鲜明。
   部分成功/失败与普通“有未保存更改”挤在底部同一位置。
4. LLM 关闭后配置完全隐藏，页内容过少；用户缺少服务类型、作用和下一步的清晰解释。
5. 透明度是 NumericUpDown，只修改真实 HUD 的 Opacity，空闲时 HUD 不可见，所谓“立即预览”往往看不到效果。
6. 模型路径固定展示 DownloadDestination，即使实际复用了缓存或侧载目录；模型状态又固定写 int8，即使加载 full 模型。
   应展示实际 ModelBundle 信息，路径在就绪但已卸载时仍有意义。
7. 已有数值范围帮助，但 0 的特殊意义靠文字记忆；输入模式、资源策略没有可比较的简明选择。
   Tab 顺序、AccessibleName、焦点/高对比度和错误字段定位还缺少明确规范。

#### 建议的设计规格

以下为设计起点，尺寸统一按 96 DPI 的逻辑值缩放，最终以真实字体和屏幕验收调整。

| 项目 | 建议 |
| --- | --- |
| 窗口 | 默认约 960×720，根据工作区限制初始大小；小窗口仍保留可见 footer，正文滚动 |
| 侧栏 | 176–192 逻辑像素；品牌/副标题/导航/版本分区；选中项增加细条或清晰轮廓，焦点态独立 |
| 内容 | 左右 24–28 间距、卡片 18–20 内边距、统一 8 的间距节奏；正文宽度有上限 |
| 字体 | 系统 UI 字体与中文回退；正文 10–11pt、辅助 9–10pt、页标题 18–20pt；有限字体集合 |
| 控件 | 输入框/下拉/按钮可见高度约 34–36；避免大量局部 Paint 仿制复杂控件 |
| 字段行 | 常规行短说明在左、编辑器约 260–340 宽；地址/Key/模型采用整行输入，窄宽时上下排列 |
| 颜色 | 一个强调色、正文/次级文字两级、背景/卡片/边线三级；状态带图标与文字，适配系统高对比度 |
| 按钮 | 全窗“保存并应用”为主要蓝色动作；页内通常中性，下载未完成等关键当前动作按状态突出 |
| footer | 固定；dirty 简短，错误持久并提供“查看问题”；保存成功单独展示，避免一编辑就抹掉失败原因 |
| 辅助功能 | 合理 Tab 顺序、可见焦点、字段标签与 AccessibleName、键盘操作折叠项；错误能定位页面和字段 |

各页建议如下：

| 页面 | 主要内容与调整 |
| --- | --- |
| 听写 | 快捷键大字/键帽 + 录制按钮；按住/切换两种模式各有短说明；设备下拉提供刷新与完整名称；识别语言跟在设备之后 |
| 语音模型 | 单一状态卡：真实路径、实际量化类型、准备进度与一个主动作；运行策略提供“快速响应/节省内存/自定义”，映射现有字段 |
| 智能纠错 | 关闭时保留解释和启用入口；启用后地址、密钥、模型全宽；密钥显隐按钮；测试结果绑定配置快照；技术参数折叠 |
| 外观与通用 | HUD 位置用三个简单示意选项与隐藏选项；透明度滑条 + 数值 + 内嵌静态预览；自启与语言单独一组 |
| 诊断与帮助 | 麦克风、模型、热键/输入权限分开状态；人工检测优先；日志/配置入口；UIPI 的说明明确结果会进入剪贴板 |

“快速响应/节省内存”先映射现有配置，不立即引入更多底层旋钮：快速响应＝预加载且常驻；
节省内存＝按需加载/有界空闲卸载，具体时间根据基准确定。用户选择自定义时再出现分钟数。
模式切换的映射必须避免把用户已手调的值悄悄重置。

## 5. 唤起与热路径优化

### 当前链路与主要成本

```text
按键 → UI 投递 → 设备枚举/WASAPI 打开 → 音频回调 → WDL 转换
     → AudioChunker(float→byte) → 投递线程 → UI → byte→float → 累积缓冲
     → ASR 串行队列 → fbank → LFR → CMVN → 扁平 tensor → ORT → CTC
     → UI → 可选 LLM → 剪贴板快照/写入 → SendInput → 延时恢复
```

首个可见预览至少要等约 600ms 音频块再加推理/投递，设备唤起速度和首个文本速度是两项指标。
当前常驻服务正常空闲没有周期录音，ASR 线程阻塞等待任务；不能把“常驻模型较大”误称为“CPU 一直忙”。

### WT-13：先补重采样协议测试

[AudioCaptureService](Services/AudioCaptureService.cs#L294) 使用 BufferedWaveProvider 的临时短读驱动
[WdlResamplingSampleProvider 2.2.1](https://raw.githubusercontent.com/naudio/NAudio/v2.2.1/NAudio.Core/Wave/SampleProviders/WdlResamplingSampleProvider.cs)。
关闭 ReadFully 防止无限补零是已有正确修复；但 pull wrapper 会把源短读交给 ResampleOut，
[WdlResampler](https://raw.githubusercontent.com/naudio/NAudio/v2.2.1/NAudio.Core/Dsp/WdlResampler.cs) 把少于 requested 的输入作为 flush，
并走临时补零/数组调整路径。实时源“当前没更多数据”与“输入最终结束”在此没有区别。

这证明存在协议与分配风险，**还不能仅凭源码断言识别错误或样本数已漂移**。
Stop 又只 drain chunker，没有显式处理剩余输入/滤波尾部。
下一轮应建立可独立测试的转换器，输入驱动或按真实可用样本量转换，只有显式 Complete 时刷新尾部。

验收 16/44.1/48kHz、mono/stereo、不同不规则分块、空输入、连续正弦、短语开头/结尾与突然停止；
比较一次供给与流式供给的样本计数/波形，规定滤波延迟容差，检查不会持续生成静音。
此项同时影响正确性与性能，比先替换 FFT 更有价值。

### WT-14：优化分配要按体量排序

| 开销 | 结构证据 | 建议 |
| --- | --- | --- |
| 120s 预留音频数组 | 每会话 `120×16000×4=7,680,000` 字节，约 7.32MiB；是容量算式，不是 RSS 实测 | 测短句大量重复时的 LOH/GC；考虑由音频所有者管理的可复用数组或块式缓冲 |
| 特征多级数组 | fbank、LFR、CMVN 各自结果，再复制 flatFeats；每个阶段有逐帧数组 | 优先合并 LFR+CMVN 写最终扁平张量，随后让 fbank 使用扁平工作区 |
| waveform scaled | 每次 Recognize 复制/缩放整段音频 | 保持原有浮点运算顺序，考虑每帧复制时缩放，复用 FFT 工作区 |
| byte 往返 | 600ms 是 9600 float，38,400 字节；float→byte→float→累积数组 | 进程内直接传有明确生命周期的 float 音频块；改接口需同步迁移所有消费者 |
| logits | 如有效帧数约 2000，则 `2000×25055×4≈200MB`；具体按模型输出 shape 测 | 保留现有 DenseTensor span 解码；不要重新引入 logits.ToArray 全量复制 |
| 全量 final | 最终结果完整复识别是产品契约，长音频决定峰值 | 按 1/5/15/30/60/120s 建基准；继续保留 120s 上限 |

float/byte 往返只有每秒数万样本，绝对带宽不大，不能声称去掉后会带来推理级的数量倍提速。
它主要是进程内接口的历史包袱和无谓分配，应在资源所有权清楚后顺手消除。

数组池必须等所有推理/预览引用退出才能归还；`RecognitionBuffer.Snapshot` 的只追加安全性不能被复用旧数组破坏。
涉及用户语音的复用缓冲要有清理策略。不能为减少 7.32MiB 分配引入污染下一会话的错误。

**算法优化边界**：保持当前模型、标点/ITN、最终整段识别、预览完整文本语义。
fbank、LFR/CMVN、CTC、模型契约变更同时评估 macOS，继续共用
`macos/Tests/VoiceTyperTests/Fixtures/`。先减少布局/复制，再依据 profiler 决定 FFT/SIMD。
浮点运算重排可能翻转 argmax，不能只以更快作为验收。

### 预览调度、ORT 线程与内存策略

现有 in-flight 跳过机制保持；最终识别排队后，尚未执行的预览应失效，避免松键后继续做一遍已不需要的预览。
已经运行的预览与 final 必须继续串行。冷加载缓存的音频回灌后也要恢复语音能量标记，否则若接下来只有静音，预览会一直延后到 final。

线程数先对比 1/2/4，不能假定越多越快；AboveNormal 的 pump 优先级也需要结合前台输入体验测量。
ORT 的自旋是延迟/功耗权衡，比较显式 `session.intra_op.allow_spinning=0/1`。
固定版本源码说明默认值取决于构建选项，不能简单把网站一般默认值当成此 NuGet 二进制的确定行为。
[ORT 1.24.2 配置键](https://raw.githubusercontent.com/microsoft/onnxruntime/v1.24.2/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h)

默认预加载且常驻暂时保留，避免没有数据就把所有用户切到频繁冷启动。
不应空闲仍开麦或高频探测来换取快唤起；设备信息可缓存并按端点变更失效，端点打开仍须处理默认设备已变化。
ReadyToRun 当前关闭，属于包体积与启动时间取舍，只做有控制的 A/B 后决定。

空闲卸载调用 `SetProcessWorkingSetSize(-1,-1)` 会修剪整个进程工作集，不能当作释放托管/原生分配的证据。
它也会影响 UI 等页的驻留，下次使用可能重新缺页；返回 bool 还应检查，而不是只 catch。
不要在显式重载后也无条件修剪；应比较是否删除这一步或仅在真正长空闲使用。
[Windows 工作集 API](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsize)

### WT-15：让指标能真实回答“唤起为什么慢”

现有数值化 `DictationMetrics` 值得保留，但 `PressedAt` 在 UI 处理热键时取值，漏掉钩子→UI 排队等待。
`CaptureStartedAt` 是 StartRecording 返回，不是设备已经送来数据；`FirstBufferAt` 用受 30ms 节流的 OnLevel 代理，
电平事件没有捕获 utterance 身份，快速重启时也可能污染新会话的 peak/静音探测。
ASR 完成时间则在 UI 收到结果后取，会混入推理线程→UI 等待。

**建议打点**：物理钩子事件、控制器接收、采集请求/成功、真实第一缓冲、尾部完成、
预览/final 入队/开始/结束、UI 收到结果、LLM 开始/结束、剪贴板准备、输入入队。
日志仍只记录数字/枚举，不记录设备名、窗口标题、识别文本。
按实际阶段计算 queue_wait、frontend、ORT、CTC，不能用 final 总时间推断具体算子慢。

### WT-17：权限探测按需且只能一个在飞

协调器每次 Probe 都 Task.Run，没有单个在飞/取消/版本控制，结果按完成顺序覆盖状态。
权限页轮询与人工连续点击可重叠，实际听写时也能再打开一个采集器。
每个 probe 还创建 AudioDelivery 线程，尽管它只需要电平而不需要 600ms 音频块。
探测固定用 Automatic，用户指定设备的问题未必能被检测。

**建议**：探测合并，繁忙听写时复用真实采集结果或推迟人工检测；与用户所选设备一致或明确写“检测系统默认设备”。
自动探测有状态变化/用户动作触发、有限重试与关闭取消；设备失败不永久 4 秒开一次设备。
`MicPermissionProbe.Classify` 在回调不足时仍返回 Available，建议保留“尚未取得数据/未知”状态，避免把能打开等同于正常采样。

## 6. 代码组织与技术债清理

不建议大规模更换框架、引入通用消息总线或为每个类都造接口。
下一轮沿资源所有权拆分，优先使上面的故障可以测试：

| 组件 | 明确的职责与所有权 |
| --- | --- |
| AppCoordinator | 创建服务与窗体、连接事件、应用生命周期；从真实状态派生托盘/设置/HUD 呈现 |
| VoiceTyperController | 唯一活跃 Utterance、阶段、结束/取消语义、目标窗口；不拥有跨会话剪贴板恢复状态 |
| ASR 生命周期服务 | 模型加载任务/配置版本/健康状态/会话租约/空闲卸载；引擎只在 pump 使用和释放 |
| CaptureContext / 采集所有者 | 一次采集的全部资源、音频转换、尾部协议、代际事件 |
| 应用级 TextInsertionService | ClipboardSnapshot、插入/复制结果、待恢复操作与关闭清理 |
| SettingsDraft / 设置应用服务 | 草稿、字段验证、外部状态冲突、保存/应用的分步骤结果 |
| ModelDownloadController | 下载任务身份、重试/取消、进度与诊断；保持现有下载器算法 |

AsrService 只需注入模型定位/构建器、串行执行器、idle 调度/时钟和 UI 投递即可覆盖关键时序；
已有 macOS ASRService 的调度/构造注入可借鉴，不把 Windows 线程模型机械改成 Swift 模式。

具体清理项：

- `ReevaluateReadinessAsync` 没有真正异步等待，保留 async + Task.CompletedTask 混淆调用契约；改为明确同步重评估，
  后台工作由可追踪任务驱动。状态回调避免同步递归不断进入同一重评估入口。
- `SaveRecognitionAsync / _saveRecognitionButton / _recognitionMessage` 已服务统一保存或独立纠错页，应按当前职责命名。
  SetupForm 内旧 Tab 注释、LocalAsrSession 的“与 WebSocket 接口逐字一致”说明也要更新。
- 去掉没有生产调用的便利接口/绘图方法时，先检查实际调用与测试，不把仍用于热键录制的 Suspend/Resume 当成死代码。
- 统一异步方法 CancellationToken 传播和 fire-and-forget 异常观测；UiDispatcher 捕获异常是最后兜底，
  不能代替会话出错后正常关闭、保存事务准确返回失败等恢复逻辑。
- 不再靠“修复编号 + 长段历史注释”表达当前不变量；代码注释说明所有权/线程/为何如此，历史移到审查与变更记录。
- 热键配置的 modifiers 也要在配置边界规范化/验证。当前校验只要求列表非空，未知值能被 BuildExpected 忽略，
  形成配置声明与实际监听不一致；避免非法修饰键悄悄退化成裸主键。

### WT-20：测试与文档的当前事实要可查

Windows Tests 目前没有专门的 AsrService 生命周期、AsrPump 关闭或真实采集上下文交错测试。
控制器假实现的 Stop 立即同步给尾帧，不能覆盖真实异步 Stop；应增加手动排队/延迟/迟到事件 harness，
不要只继续增加 happy path 参数组合来提高数量。

CI 已存在且发布 x64/arm64，不能继续写“没有 CI”。但仍有：

- 工作流只按 windows/ 路径触发，共享的 macOS ASR Fixtures 改动不触发 Windows 对照测试。
- 普通 CI 没有预置真实模型，CMVN/端到端推理能跳过；应安排有模型缓存与固定哈希的专项 job，显式要求该组不跳过。
  PR 快速测试不必每次联网下载 240MB。
- arm64 目前是交叉发布，不能代表 arm64 原生进程和硬件验收。
- 没有 packages.lock.json，也没有全局 SDK 固定策略；旧文档某些位置仍把锁文件描述为已入库。
- DESIGN 顶部更新与后文历史结论相互冲突，旧审查仍写 ReadyToRun 已启用，但当前工程明确关闭。
  建议增加精简“当前事实/验证证据/待办”页，历史方案保留日期并降为历史记录，避免重复否定当前已完成能力。

## 7. 真机测量与验收方案

### 性能目标与度量方法

先固定模型/ORT/线程数、Release 构建、硬件/电源模式/设备/DPI、是否开 LLM，再建当前版本基线。
温启动与空闲卸载后的冷恢复分别测，至少记录 p50/p95、样本量和异常次数；冷启动需分离文件缓存影响。

| 项目 | 方法 | 建议验收目标，非实测结果 |
| --- | --- | --- |
| 空闲资源 | 无窗/设置隐藏，分别引擎常驻与卸载，连续记录 CPU、唤醒、线程、句柄、Private Bytes、Working Set | 无麦克风采集、无持续推理；稳定空闲平均 CPU 可先以 <0.5% 为目标，注明采样口径 |
| 热键到反馈 | 原始钩子时间→HUD 首次呈现；右 Ctrl 150ms 延迟单独统计 | 普通组合热键 warm p95 <100ms；右 Ctrl 按既定延迟验收 |
| 热键到首帧 | 钩子事件→实际第一缓冲；内置/USB/蓝牙分别测 | 内置/USB warm p95 <200ms 作为起始目标；慢设备建立独立基线 |
| 松键到输入入队 | 1/5/15/30/60/120s，LLM off；分阶段打点 | 同机较当前基线改善，且各时长不超过既定看门狗；不能承诺所有硬件统一绝对值 |
| 冷恢复 | 卸载后短句立即松手、长句、重复取消 | 不丢开头，不假 Ready；模型加载与录音并行，记录额外 final 等待 |
| 分配/峰值 | 每个阶段 allocated bytes、LOH、Gen2 次数，ORT 前后 Private Bytes | 减少可解释的分配；正确性和首帧不回退 |
| 设置响应 | 打开、切页、字段输入、状态刷新，长文本/错误/高 DPI | 无同步设备枚举导致的长停顿；输入和焦点稳定，所有编辑器可达 |

Private Bytes/提交内存用于判断仍持有的内存，Working Set 用于观察驻留；二者要同时看。
不要调用强制 GC 或工作集修剪后仅截图任务管理器来声称泄漏解决。
初次 ORT arena 扩张允许形成新平台，真正要检查的是同类后续循环是否持续增长。

### 稳定性验收矩阵

| 场景 | 重复/持续方式 | 通过条件 |
| --- | --- | --- |
| 短句/误触/取消混合 | 1000 次不同长度，夹杂 hold/toggle、右 Ctrl 手势 | 会话/线程/句柄趋势稳定，无旧音频污染，无重复上屏 |

| 空闲卸载 | 1 分钟配置加速测试，另测用户真实时间配置 | 临界点开始会话不误卸载，恢复可识别，租约归零才释放 |
| 设备/电源 | USB 拔插、蓝牙断连/切端点、睡眠/恢复、锁屏/解锁 | 明确结束受影响会话，下一次可重建，资源各释放一次 |
| 模型异常 | 首启无模型、加载失败、文件损坏、重复重载 | 不留已完成“在飞”任务，不反复自激加载，恢复后的模型可用 |
| 推理阻塞 | 用假引擎控制不返回/超时；真实长音频另测 | 不宣称恢复但继续无限接单，不并发 Dispose 使用中的引擎 |
| 剪贴板/输入 | 图片/HTML/RTF/空内容/用户新复制/连续听写/管理员窗口 | 尽力恢复原内容、不覆盖新复制；失败提示准确，不静默丢结果 |
| 设置 | 草稿关闭重开、非法值、保存失败、外部自启变更、测试期间改字段 | 草稿保留、规范化一致，部分成功可理解，拒绝操作不改变会话阶段 |
| DPI/界面 | 中英文、不同缩放/双屏、窄工作区、高对比度/键盘 | 内容和操作可达，HUD 位置正确、不抢焦点，错误可阅读 |
| 退出 | 录音/模型加载/预览/final/LLM/下载/探测中退出 | 不使用已释放队列/控件，不残留后台采集或迟到插入 |

测试资源使用独立临时目录/测试账户，不修改用户真实密钥、配置、模型和剪贴板。
真实麦克风/剪贴板/权限与 arm64 验收记录必须独立于“单测通过”“交叉发布成功”。
