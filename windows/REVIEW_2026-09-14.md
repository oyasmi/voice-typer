## 1. 审查基线与方法

- 审查日期：2026-09-14。审查基线：`9bc6036`（Windows 应用版本 `3.2.1`，macOS `3.4.0`）。
- 方法：Windows 全量源码（约 5.3k 行）与 macOS 全量源码（约 7.4k 行）逐模块对读；
  比对两侧测试用例、构建脚本、安装脚本与设计文档；核对 `macos/` 自 `86424eb` 以来的
  7 个提交，确认哪些行为变更没有同步到 Windows。
- 环境限制（与上一轮相同，必须继续如实标注）：**Linux、无 .NET SDK、无 Windows 真机**。
  本文**没有**编译、没有运行测试、没有做任何性能测量。所有性能相关结论都是"存在可优化的
  结构性开销"，不是实测数字；带 ⚠️ 的条目在动手前必须先在真机上建立基线。
- 严重程度沿用上一轮口径：P0 阻断主流程 / P1 影响主要使用路径 / P2 体验与工程完善。
  证据口径：**S** 源码可明确证明 · **C** 结合依赖契约确认 · **R** 产品或工程取舍建议。

### 一句话结论

Windows 的**识别管线与可靠性骨架**已经和 macOS 同构，真正的差距在**"应用层"**：
macOS 在 `3.2.1 → 3.4.0` 之间做的一整批首启引导、HUD 反馈、就绪反馈与下载优化
（提交 `88fd343`、`2ebab09` 及其后的默认值调整）**一项都没有移植到 Windows**。
这批差异不是"少几个选项"，而是决定了新用户第一次按下热键时能不能得到反馈。
加上 Windows 至今**没有任何一次真实编译与测试运行**，本轮的最高优先级建议其实是
**先建 CI**——它能把 `REPAIR_DELIVERY.md` 里一半以上的"待验证"直接变成"已验证"。

## 3. 第一类：与 macOS 的功能对等缺口

`DESIGN.md` §13/§14 把 Windows 对齐到了 macOS **3.2.1**。此后 macOS 走到 3.4.0，其中
`88fd343`（首启引导、热键触发方式与就绪反馈）与 `2ebab09`（HUD 反馈与性能优化）是两个
大批次，**Windows 完全没有收到**（3.4.0 的双语界面是唯一同步过来的）。下列缺口全部源自
这两个批次及随后的默认值调整。

### VW-01：未就绪时按下热键完全无反馈 · P1 · 中 · S

定位：[AppCoordinator](App/AppCoordinator.cs) `ReevaluateReadinessAsync` / `ActivateReadyState`、
[VoiceTyperController](Core/VoiceTyperController.cs) `Start`。

Windows 只在 `ActivateReadyState()` 里创建并启动控制器。也就是说模型缺失、下载中、加载中
这三种状态下**键盘钩子根本没装**——用户按下 `Ctrl+F2` 得到的反馈与"应用已崩溃"完全一致，
无从判断缺什么、要等多久。

macOS 在 `88fd343` 里把这条路径改掉了：只要输入监控权限具备就照常监听热键，控制器上挂一个
`blockedReason`，按下时通过 `onBlockedAttempt` 把"还缺什么"说出来（HUD 一层 + 把对应窗口摆到
面前一层，并对连按做 5 秒节流）。

**修复要点**：给 `VoiceTyperController` 增加 `BlockedReason` 字段与 `BlockedAttempt` 回调；
协调器在 `ModelMissing` / `DownloadingModel` / `ModelLoading` 三个分支调用一个
`GateHotkeyListening(reason)`（启动控制器但只提示不录音），在就绪分支清空；HUD 用现成的
`ShowError` 展示原因。Windows 没有 TCC 门，反而比 macOS 更简单——不存在"钩子装不上"的分支。

### VW-02：无首启引导 · P1 · 高 · S/R

macOS 的四步引导（欢迎 → 权限 → 模型 → 试一试）最后一步会让用户在引导窗口里**真的完成一次
听写**，把"热键 → 麦克风 → 识别 → 插入"整条链跑通，哪一环出问题当场指出
（`OnboardingViewModel` + `OnboardingDictationEvent`，含 156 行单测）。

Windows 现在只有：首次探测到麦克风被拒 → 打开设置窗口的权限页。用户拿到的信息是
"麦克风权限可能被禁用"，但不知道模型有没有下载完、热键会不会被别的软件占用、
目标应用会不会拒绝粘贴。考虑到 Windows 的失败模式**比 macOS 多**（UIPI 提权窗口、
AV 拦钩子、剪贴板被占用），"能不能用"的验收反而更需要真跑一次。

这是 WR-012 的延续，上一轮标记为"未做"。建议实现为一个独立的 `OnboardingForm`，直接复用
协调器已有的 `StateChanged` / `PreviewUpdate` / `RecognizedText` 事件流，不必新造机制。

### VW-03：HUD 反馈缺口 · P1 · 中 · S

对照 [RecordingHud](UI/RecordingHud.cs) 与 `macos/.../RecordingHUDController.swift`：

| 能力 | macOS | Windows | 影响 |
| --- | --- | --- | --- |
| 实时电平波形 | 有（`onAudioLevel` → `WaveformView`，30ms 节流） | **无**（`AudioCaptureService` 根本没有 `OnLevel` 回调） | 用户无法判断"它到底有没有在听我说话" |
| 状态行显示输入设备名 | 有（`AudioInputDevice.currentName()`，超长截断） | **无** | 选错输入设备时没有任何线索 |
| 持续静音主动提示 | 有（录音后 1.5s / 4.5s 两次探测，RMS 低于阈值就提示检查麦克风） | **无** | 对着静音的麦克风说完一整段才发现结果是空的 |
| 识别结果为空的专门提示 | 有（`showNoSpeech`，与"错误"区分，给的是"去检查麦克风"这条线索） | **无**，直接静默回 Idle | 分不清"没识别到"和"插进去了没看见" |
| 等待 LLM 校对的独立状态 | 有（`setCorrecting`，蓝点 +"校对中…"） | **无**，一直显示"识别中" | 分不清在等本地推理还是在等网络（最长 `llm.timeout` 秒） |
| 预览排版 | 双行、随内容动态增宽、按屏幕宽度封顶 | 单行、固定 320×90、只保留尾部 | 长句只剩尾巴，而"边说边校对"正是 HUD 存在的理由 |

其中**电平波形与静音探测是一组**：两者都依赖 `AudioCaptureService` 增加一个
`Action<float>? OnLevel`（在 WASAPI 回调里算一次 RMS，几乎零成本），是本组的前置项。
`AppConstants` 需要补 `SilenceRmsThreshold`（macOS 的 `silenceRMSThreshold`）。

### VW-04：识别中不能按 Esc 取消 · P1 · 低 · S

[HotkeyStateMachine](Services/HotkeyStateMachine.cs) 只在 `Engaged`（按住录音）状态受理 Esc，
[VoiceTyperController](Core/VoiceTyperController.cs) `CancelByUser` 也要求 `_isRecording`。
macOS 在松键之后到结果上屏之前仍然受理 Esc（`hotkeyService.acceptsCancelWhenInactive`），
因为"别把这段写进去"的诉求在识别阶段同样成立——尤其 Windows 上识别可能比 macOS 慢。

根 README 已经把这条差异如实写成"Windows 目前限录音中"，所以这是**已知**缺口，但修复成本很低：
状态机加一个"松键后仍接受 Esc"的窗口，控制器在 `OnTailChunk` 打开、在收尾时关闭。

### VW-05：无切换式热键（hold / toggle）· P2 · 低 · S

`HotkeyConfig` 没有 `mode` 字段。macOS 的 `HotkeyMode.toggle` 是为长口述准备的
（写邮件、写文档时手指不必一直按住），且**刻意不做**"短按 toggle / 长按 hold"的自动判别
（理由见 `AppConfig.swift` 的注释——误触的代价会从"什么都没发生"升级成"一直在录"）。
移植时请把这条取舍一并带过来。

### VW-06：模型加载策略的配置缺口与默认值漂移 · P2 · 低 · S

- `AsrConfig` 缺 `preload_on_launch`。Windows 目前**总是**在启动后立刻
  `PreloadAsync()`（`ProbeMicrophone(isFirstProbe: true)` 里），也就是说开机自启的用户
  一定会为一次可能不发生的听写常驻约 500MB。macOS 把它做成了可关闭的选项，且关闭时
  `prepareWithoutLoading()` 只确认文件在不在、状态落到 `SuspendedForIdle`。
  Windows 缺这条路径——`AsrService` 没有 `PrepareWithoutLoadingAsync` 的对应物。
- `IdleUnloadMinutes` 默认 **10**，注释写着"默认值与 macOS 保持一致（W-30）"。
  这句已经过期：macOS 在 `8e2e7fd` 把默认改成了 **0（从不）**，与"启动预加载默认开启"配套。
  要么跟随改成 0，要么把"Windows 内存更敏感所以保留 10 分钟"写成 §13.1 的有意分歧——
  但不能让注释继续说谎。

### VW-07：无 HUD 位置设置，且当前落点与 macOS 相反 · P2 · 低 · S

`UIConfig` 缺 `hud_position`（macOS 有四档：底部居中 / 右下角 / 跟随光标 / 不显示；
其中"不显示"只静音**过程**，错误提示仍会浮出来）。

更值得注意的是：[RecordingHud](UI/RecordingHud.cs) `PositionNearForegroundWindow` 用的是
`y = wa.Top + 80`——HUD 显示在**屏幕顶部**。macOS 的默认落点是屏幕底部（`bottomInset = 80`，
为避开 Dock）。这不是"有意分歧"，`DESIGN.md` §13.1 里没有这条记录。Windows 的任务栏默认在
底部，所以"底部居中 + 避开任务栏"同样成立。建议先把默认落点与 macOS 统一，再补位置选项。

### VW-08：模型下载缺分段并发与退避重试 · P2 · 中 · S

[ModelDownloader](Asr/ModelDownloader.cs) 是单流顺序下载 + 每文件最多 2 次本地重试。
macOS 在 `2ebab09` 里加了：≥32MB 的文件走 **4 段并发**下载（241MB 的 `model_quant.onnx`
正是唯一命中项），协调器侧再加 **5s / 20s / 60s 的退避自动重试**，并把
"将在 N 秒后自动重试（第 x/3 次）"写进界面文案。

Windows 侧的 `.part` 续传设计本身比 macOS 的 `.resume` 更干净（§13.1 已记录），分段下载
可以直接建立在它之上：按 `Range` 拆 4 段写同一个 `.part` 的不同偏移（`FileStream` 定位写入），
失败退化回单流。首启体验的收益很直接——241MB 在单连接下经常受限于单流带宽。

### VW-09：无"检查更新"入口 · P2 · 低 · S

macOS 托盘菜单有"检查更新…"（`UpdateChecker` 读 GitHub releases，只在用户主动点击时跑一次，
不做后台轮询）。Windows 托盘菜单只有"关于"。这一项几乎可以逐行直译，
`HttpClient` + 版本号比较 + `MessageBox`，注意沿用"不做后台自动检查"的取舍。

### VW-10：预览没有跳过静音段 · P1 · 低 · S

[LocalAsrSession](Asr/LocalAsrSession.cs) `SchedulePreview` 只要有新音频就排预览。
macOS 在 `2ebab09` 里加了 `hasSpeechSinceLastPreview`：两次预览之间如果全是静音，
就跳过这一轮整窗重跑——注释里记的实测收益是**稳态约 28% 单核**，而口述中的思考停顿占比不低。
判错的代价上限只是多跑或少跑一次预览（松手后的 `finalize` 永远对完整音频整段重跑）。

这一项在 Windows 上收益**只会更大**（CPU 更慢、没有 Accelerate），而实现成本是一个 RMS 门限。
注意：移植它必须**同时**修 VW-12，否则跳过会让窗口右侧累积超过一个预览窗。

## 4. 第二类：Windows 侧新发现的缺陷

以下问题不在 WR-001…WR-020 与 R0–R4 的清单里，是本轮对读时新发现的。

### VW-11：模型缺失时反复抢焦点，且设置窗口此后不再自动隐藏 · P1 · 低 · S

定位：[AppCoordinator](App/AppCoordinator.cs) `ReevaluateReadinessAsync` 的 `ModelMissing` 分支、
`OpenSetup`、`HideSetupWindowIfVisible`。

```csharp
case AsrState.ModelMissing:
    _currentState = AppStateInfo.ModelMissing;
    OpenSetup(SetupTab.Recognition);   // ← 每次重评估都执行
    break;
```

`OpenSetup` 最终调用 `form.Present()` → `BringToFront()` + `Activate()`，**每次**都会抢焦点。
`ReevaluateReadinessAsync` 由 `AsrService.OnStateChange` 无差别触发，用户点"取消下载"之后
会立刻再吃一次弹窗——这正是 macOS 记录过的 B7 现象（"点了取消下载，窗口反而跳到最前面"），
macOS 用 `forcedPresentations` 集合修掉了：每个理由在一次未就绪期内只抢一次焦点，恢复就绪时清空。

更隐蔽的第二个后果：`OpenSetup` 无条件设置 `_userOpenedSetup = true`，而
`HideSetupWindowIfVisible()` 的第一行就是 `if (_userOpenedSetup) return;`。于是**任何一次自动
弹窗**都会让"就绪后自动收起设置窗口"这条路径永久失效。同一问题也存在于首次麦克风探测被拒
时的 `OpenSetup(SetupTab.Permissions)`。

**修复要点**：区分"用户主动打开"与"系统强制展示"两条入口（macOS 的
`setupControllerIfNeeded(forceShow:)` 就是这么分的）；强制展示按理由去重。

### VW-12：预览滚窗只滚一次，慢机器上可能失控 · P1 · 低 · S

定位：[RecognitionBuffer](Asr/RecognitionBuffer.cs) `Preview`。

```csharp
if (count - _committedN > _previewWindowSamples) { Roll(buffer, count); }
```

每次 `Roll` 只把 `_committedN` 前移约**半个窗口**。`_previewInFlight` 会跳过排队中的预览，
因此两次预览之间累积的音频可能超过半个窗口——一旦单次预览耗时长到这个程度，
窗口右侧就会**单调增长**，而预览耗时正比于窗口长度，形成正反馈。这恰恰是 Windows
（CPU 更慢、`preview_window` 自校准到 6s 时半窗只有 3s）比 macOS 更容易踩到的情形。

macOS 的同名函数已经改成 `while`，并在注释里写明了终止性证明（切点落在
`committedN + 窗口/2` 附近，搜索半径仅 100ms，每轮严格推进）。Windows 直接跟改即可，
一行的事。**移植 VW-10 之前必须先改这里。**

### VW-13：听写进行中被模型状态变化覆盖托盘状态 · P2 · 低 · S

`ReevaluateReadinessAsync` 的 `Unloaded` / `Loading` 分支无条件写
`_currentState = AppStateInfo.ModelLoading`，不看当前是不是正在录音。空闲卸载后首次按热键
正好命中：引擎进入 `Loading`，托盘立刻显示"模型加载中…"，盖掉"录音中"。

macOS 在 `bf06f23` 专门修过这条（`computeTargetState` 的 `previous` 参数在 `.loading` 与
`.ready` 两个分支保留活动听写态，并配了 `AppCoordinatorReadinessTests` 的回归用例）。
Windows 的后果比 macOS 轻——不会 `Stop()` 掉控制器、不会丢音频，只是托盘文字跳变——
但仍应修，而且顺手能把 macOS 那套"纯函数 `ComputeTargetState` + 副作用分离"的可测结构带过来
（见 VW-24）。

### VW-14：HUD 尺寸按像素硬编码 · P2 · 中 · C

`app.manifest` 声明了 `PerMonitorV2`，`Program.Main` 也调了
`Application.SetHighDpiMode(HighDpiMode.PerMonitorV2)`。但 [RecordingHud](UI/RecordingHud.cs)
构造时写死 `Size = new Size(320, 90)`，`OnPaint` 里的 `paddingX = 18`、圆角 14、点 10px
也都是像素常量。字体用 pt 会随 DPI 缩放，**窗口不会**——150%/200% 缩放的屏幕上会出现
"字撑满甚至溢出固定大小的浮窗"。同时 `PositionNearForegroundWindow` 用 `Screen.WorkingArea`
（物理像素）算落点，跨不同 DPI 的多屏拖动时也需要重新确认。

**修复要点**：所有几何常量改为按 `DeviceDpi` / `AutoScaleDimensions` 换算，或直接改用
`Dpi­ChangedAfterParent` 事件重算；HUD 真机验证清单里加上 100%/150%/200% 三档。

### VW-15：保存配置时销毁并重建 HUD · P2 · 低 · S

`ReloadConfigurationFromDisk()` 里 `_hud?.Dispose(); _hud = new RecordingHud(_config.UI);`。
任何一次非 UI 配置保存（改热键、改识别语言）都会连带重建 HUD 窗口句柄。macOS 记录过同样的
问题（B8），改成了 HUD 长生命周期 + `updateConfig(_:)` 就地生效。Windows 当前因为活跃听写期间
会拒绝保存，所以后果有限，但一旦补上 VW-07 的位置设置就会变成真实问题（位置改动要到下次
重建才生效）。建议现在就改成 `_hud.ApplyConfig(_config.UI)`。

### VW-16：麦克风选 `Role.Communications`，且没有输入设备选择 · P2 · 中 · C/R

[AudioCaptureService](Services/AudioCaptureService.cs) `Start` 用
`GetDefaultAudioEndpoint(DataFlow.Capture, Role.Communications)`。Windows 的"默认设备"与
"默认通信设备"是**两个独立设置**，用户在声音设置里选的默认录音设备经常不是通信设备
（典型：把会议耳机设成默认通信设备，把电容麦设成默认设备）。结果是听写用的可能不是用户
以为的那支麦克风，而 HUD 又不显示设备名（VW-03），用户没有任何线索。

另外 [MicPermissionProbe](Core/MicPermissionProbe.cs) 靠**真的打开一次 WASAPI 采集**来探测，
启动时一次、权限页打开后每 4 秒一次——会让系统托盘的"麦克风使用中"指示灯反复闪烁
（§13.2 已把观感列为待确认，但没提设备选择这一层）。

**建议**：(a) 改用 `Role.Console`（或提供可选项），与"用户在声音设置里看到的默认录音设备"
一致；(b) 设置页增加输入设备下拉（`MMDeviceEnumerator.EnumerateAudioEndpoints`），
这是 Windows 用户的常规预期，macOS 侧因为系统级设备切换更顺手而没做；
(c) 权限页轮询改为"窗口可见且用户停留在权限页"时才跑，减少指示灯闪烁。

## 5. 第三类：Windows 特性带来的优化空间

> ⚠️ 本节所有条目都需要**先在真机上建立基线**（录 10s / 60s 各三次，记录预览 RTF、
> finalize 耗时、峰值工作集、稳态 CPU），再按收益排序动手。不要把下面的结构性分析
> 当成实测结论。

### VW-17：音频分帧路径的无谓开销 · P2 · 中 · S

[AudioChunker](Services/AudioChunker.cs) 用 `Queue<float>` **逐样本** `Enqueue`/`Dequeue`，
并把 chunk 编码成 `byte[]`；[LocalAsrSession](Asr/LocalAsrSession.cs) `SendAudio` 收到后又
`Buffer.BlockCopy` 解回 `float[]`。这条 float → byte → float 的往返是旧 WebSocket 协议
（`client-server/PROTOCOL.md`）的遗留，进程内没有任何意义。

更值得注意的是调用位置：`AudioCaptureService.AppendSamples` **持有 `_lock`** 调用
`_chunker.Append`，而它跑在 WASAPI 回调线程上。16kHz 下每秒 16000 次队列操作 + 每 600ms 一次
38KB 分配，全在采集线程的临界区里。

**优化要点**：`AudioChunker` 改为固定容量 `float[]` 环形缓冲，`Append` 用 `Span.CopyTo`；
回调签名从 `Action<byte[]>` 改为 `Action<float[]>`（或 `ReadOnlyMemory<float>` + 池化）。
改动面局限在 `AudioChunker` / `AudioCaptureService` / `LocalAsrSession` 三个文件，
`AudioChunkerTests` 需同步改断言。

### VW-18：特征前端的锯齿数组三级分配 · P2 · 中 · S ⚠️

`FbankFrontend.Compute` 返回 `float[][]`（每帧一个 80 维小数组）→ `LfrCmvn.ApplyLfr` 再产出
`float[][]`（560 维）→ `ApplyCmvn` 再产出一份 `float[][]` → `SenseVoiceEngine.Recognize`
最后又 `Array.Copy` 展平成一个 `float[]` 喂给 `DenseTensor`。

120 秒 finalize 的量级：约 12000 个 80 维数组 + 2000 个 560 维数组 ×2 + 一块 4.5MB 的展平缓冲，
即**约 16000 次小对象分配 + 三次全量拷贝**，全部发生在用户松手之后、结果上屏之前的关键路径上。
macOS 侧因为走 Accelerate 的连续缓冲 API 天然没有这层结构。

**优化要点**：三个阶段改为写入**单块连续缓冲**（`float[]` + stride 索引，或
`ArrayPool<float>.Shared`），`Compute` 直接产出 `[numFrames * numMelBins]`，LFR/CMVN 就地或
写入第二块复用缓冲，最后零拷贝地包成 `DenseTensor`。**必须在改动前后跑金标准夹具
（`FbankParityTests`，阈值 1e-3 不得放宽）**——这是识别质量的红线。

### VW-19：实数输入却做完整复数 FFT · P2 · 中 · S ⚠️

[Rfft](Asr/Rfft.cs) 的类名叫 Rfft，实现却是标准的 radix-2 **复数** FFT，实数输入时虚部置零。
类注释坦白了这个取舍（"比 macOS 那套打包实数 FFT 更简单"）——正确，但 512 点变换的一半工作量
是白做的，而它每 10ms 一帧地跑在识别热路径上。

**优化要点**：标准的 N/2 点复数 FFT + split 后处理（打包实数 FFT），或保留现实现但用
`System.Numerics.Vector<float>` 向量化蝶形运算。前者省约一半算力但要重新过金标准；
后者改动小、风险低。**建议先测**：如果 fbank 在总 RTF 里占比很小（ORT 推理通常是大头），
这一项就不该优先做。`FftTests` 已有 3 个用例可作回归基线。

### VW-20：未启用 ReadyToRun · P2 · 低 · R ⚠️

`csproj` 已明确拒绝 `PublishSingleFile` 与 `PublishTrimmed`（理由充分，见注释），但没有评估
`PublishReadyToRun`。WinForms 的冷启动 JIT 成本不小，而这是一个**开机自启**的常驻工具——
启动速度直接决定用户登录后多久能用上热键。R2R 是纯粹的"体积换启动时间"，不引入
`PublishSingleFile` 那类自解压与 AV 误报风险，与目录式部署完全兼容。

**建议**：真机上分别测 `dotnet publish` 有无 `-p:PublishReadyToRun=true` 的冷启动耗时与
目录体积，按数字决定。arm64 需要在 arm64 机器上或用交叉 R2R 产出。

### VW-21：托盘状态图标每次重绘 · P2 · 低 · S

`TrayController.ApplyStateIcon` 每次状态变化都 `new Bitmap(32,32)` → GDI+ 绘制 → `GetHicon`
→ `Icon.FromHandle().Clone()` → `DestroyIcon`。一次听写至少经历
Idle → Recording → Recognizing → Inserting → Idle 四次重绘。状态只有 11 种且图形是静态的，
构造时预渲染并缓存即可，顺带消掉 GDI 句柄反复申请/释放这一整类风险。

## 6. 第四类：工程与可验证性（本轮最高优先级）

### VW-22：没有 CI，且 `packages.lock.json` 缺失 · P0 · 低 · S

仓库根目录**没有 `.github/`**，两个平台都没有任何自动化构建。对 macOS 影响有限
（作者本机天天在用），对 Windows 则是致命的：`REPAIR_DELIVERY.md` 里每一条都写着
"代码完成，待 `dotnet build` 确认"，而这个确认**至今没有发生过**。

同时 `DESIGN.md` §11 的风险对策栏写着"`packages.lock.json` 入库（`RestorePackagesWithLockFile=true`）"，
但仓库里既没有该文件，`csproj` 里也没有该属性——文档与现实不符。

**建议（应当排在所有其它条目之前）**：加一个 `windows-latest` 的 GitHub Actions 工作流：

```yaml
# 最小可用形态
- dotnet restore  (开启 --locked-mode，配合入库的 packages.lock.json)
- dotnet build VoiceTyper.sln -c Release          # 消掉"能不能编译"
- dotnet test  Tests/VoiceTyper.Tests             # 消掉"测试能不能跑绿"
- dotnet publish -r win-x64   --self-contained    # 消掉"能不能发布"
- dotnet publish -r win-arm64 --self-contained    # 消掉 arm64 变体风险
- 断言 dist/ 里没有 xunit.* / VoiceTyper.Tests.dll （R0-1 的验收项）
```

这一步的性价比远高于本文其它任何条目：它把 WR-001、R0-1/R0-2/R0-3、以及 `NativeLayoutTests`
（`Marshal.SizeOf<INPUT>() == 40`，只有在真实 Windows 进程里跑才算数）一次性从"待验证"
变成"已验证"，而且此后每次改动都自动回归。剩下真正需要人手的只有麦克风、剪贴板、
热键穿透、安装卸载这几类——那张清单会短很多。

### VW-23：测试规模与关键覆盖 · P1 · 中 · S

当前 **97 个用例（Windows） vs 188 个（macOS）**。缺口集中在：

| 缺失的测试 | macOS 对应 | 为什么重要 |

### VW-24：`AsrService` 不可注入 · P1 · 中 · S

macOS 的 `ASRService` 构造函数接受 `idleScheduler` / `modelLocate` / `engineFactory` 三个注入点
（"仅供测试注入"），因此空闲卸载、重载去重、加载代际丢弃这些时序逻辑都能用假引擎 + 可控时钟测。
Windows 的 [AsrService](Asr/AsrService.cs) 直接 `new SenseVoiceEngine(...)`、直接 `new Timer`，
一个用例都写不了——而这恰恰是 R2-2/R2-3 两个 P1 缺陷所在的模块。

同理，`AppCoordinator` 的就绪判定是一大坨带副作用的 `switch`；macOS 把它拆成了纯函数
`computeTargetState(...)` + 副作用执行两半，才有了 `AppCoordinatorReadinessTests`。
修 VW-13 时顺手做这个拆分，成本几乎为零。

### VW-25：版本号口径 · P2 · 低 · S

- `csproj` 的 `<Version>3.2.1</Version>`，注释说"对齐 macOS 3.1.9 / 3.2.1 行为基线"；
- `app.manifest` 的 `assemblyIdentity version="3.0.0.0"`（从未随版本更新）；
- 双语界面（macOS 3.4.0 的特性）已经合入 Windows，但版本号没动。

建议：本轮修复落地后统一升版，并在 `CHANGELOG` 层面给 Windows 一份自己的记录
（目前只有 `macos/CHANGELOG.md`），`app.manifest` 的版本随之同步。
